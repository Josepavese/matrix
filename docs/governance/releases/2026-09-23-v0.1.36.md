This release makes ACP authentication run the method the agent itself advertises,
instead of a hardcoded one, and gives the advertised capability its first
consumer.

## What The Release Contains

- `onboarding.AgentAuthController`: a narrow port over the protocol side, wired in
  `cmd/matrix/run.go` to the same router the runtime uses.
- The generic ACP auth handler reads the agent's own `authMethods` and offers
  those; the hardcoded API-key method is reserved for agents that publish none or
  cannot be reached.
- Completing an advertised method performs the protocol `authenticate(methodID)`;
  a rejection is reported as a failure rather than as a successful-looking empty
  result.
- `docs/matrix_agent_auth.md` documents the boundary, the missing credential
  lifecycle and the two-writers-one-file contention.
- The issue that drove the work is closed with its resolution in
  `issues/closed/2026-09-23-acp-auth-unwired-and-credential-has-no-lifecycle.md`.

## Windows Validation

All nine checks passed on the Windows 11 IoT Enterprise LTSC guest:
`matrix.exe` runs and reports `matrix 0.1.36`, `doctor` exits 0, `readiness`
reports the missing vault as a blocker, and configs are seeded without
overwriting.

The first attempt failed, and the failure is worth recording because it was not
caused by the release:

- `install.ps1` reported `Expected exactly one Matrix release asset for
  windows_amd64 in Josepavese/matrix v0.1.36, found 0`.
- The release has nine assets. `GET /repos/.../releases/394477175/assets`
  returns all nine; `GET /repos/.../releases/tags/v0.1.36` returned an **empty
  asset list** and was still returning it forty minutes after publication. The
  by-tag release document was stale while the assets were downloadable, so
  `gh release view`, `gh release list` and `install.ps1` all agreed on a
  zero-asset release that did not exist.
- `install/install.ps1` now falls back to the id-addressed asset endpoint when the
  tag-addressed view reports no assets, and says so when it does. The fallback was
  verified against the live v0.1.36 release: the patched installer installed
  `matrix 0.1.36` on Windows and all nine checks passed.
- `tests/windows_release_validation.ps1` gained `-InstallerUrl`, which is how a
  corrected installer is exercised before it is published.

Consequence for the published release: the `install.ps1` shipped in **v0.1.36 is
the unpatched one**, so a Windows install of v0.1.36 can hit the stale index and
fail until GitHub's by-tag view refreshes. The fixed installer is on `main`; a
v0.1.37 would be the way to make the downloadable installer the corrected one.
Linux and macOS installs use `install.sh`, which queries the same by-tag endpoint
and has the same exposure; the archives themselves are unaffected and download
normally.
