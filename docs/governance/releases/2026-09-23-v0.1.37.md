This release exists for one reason: the installer published with v0.1.36 could not
see that release's own assets. The correction is described in
[2026-09-23-v0.1.36.md](2026-09-23-v0.1.36.md); this document records the release
that carries it and the proof that it works.

## Why A Release Was Needed At All

`install.ps1` read the release document addressed by tag. For both v0.1.36 and
v0.1.37 that endpoint returned an **empty asset list** while
`/releases/<id>/assets` returned all nine assets and the archives downloaded
normally:

| Query | v0.1.36 | v0.1.37 |
| --- | --- | --- |
| `releases/tags/<tag>` | 0 assets | 0 assets |
| `releases/<id>/assets` | 9 assets | 9 assets |

`gh release view`, `gh release list` and `install.ps1` all read the stale
by-tag document and agreed on a zero-asset release that does not exist. Fixing the
installer in the repository does not fix a copy already published, so the corrected
installer had to be published in a release of its own.

## What Changed

- `install/install.ps1` falls back to the id-addressed asset endpoint when the
  tag-addressed view reports no assets, and says so when it does.
- `tests/windows_release_validation.ps1` gained `-InstallerUrl`, which is how a
  corrected installer is exercised before it is published.

`install.sh` has the same exposure on Linux and macOS (it reads the same by-tag
endpoint). It was **not** changed here, and that is deliberate: the fallback is
verified on Windows only, and the shared installer behaviour is worth deciding
once rather than twice. It is recorded as the next step below.
