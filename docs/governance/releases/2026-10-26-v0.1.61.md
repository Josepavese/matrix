# Matrix v0.1.61 — shared immutable agent artifacts and regenerable software

Installed agent software no longer has to be copied once per PAL home. A binary
artifact Matrix already verified can be published once into an immutable,
digest-addressed store, and every home can register the agent against a verified
generation of it with a small reference instead of its own 78 MB copy. The same
release gives a consumer a deterministic inventory and a restore path, so
regenerable software can be left out of a data backup without losing
recoverability.

The release answers the external report
[agent copies per worker and Hub backup peak](../../../issues/closed/2026-10-26-external-agent-artifact-dedup-hub-backup-peak.md)
in part and with declared limits: acceptance is a decision to investigate and
qualify a report, not a commitment to build every part of it
([issue governance](../issue_governance.md)). The report's Hub backup peak, its
disk reserve and its per-worker inventory are not changed by Matrix; what Matrix
now provides is the contract that makes excluding regenerable software a measured
consumer decision instead of a blind copy.

## The contract

- A generation is addressed by the sha256 Matrix already verifies against the ACP
  registry index. `matrix agent store publish` downloads, verifies, extracts,
  manifests and publishes it **atomically**; it refuses an artifact the index does
  not publish a valid digest for, and a re-publish with different bytes or
  immutable fields under the same digest is refused.
- Publication removes write bits from the tree and records the exact post-seal
  modes in a tree manifest (path, mode, size, sha256). Executables stay
  executable: a store that cannot run what it stores only moves the problem.
- `matrix agent store verify <digest>` recomputes the manifest offline and
  compares it exactly. This is the evidence a consumer can re-run without the
  network or the registry.
- A home installs with `matrix install <agent> --store <root>`: the record and the
  absolute launcher point into the generation, and the Vault carries an
  `ArtifactReference` (store, digest, tree-manifest digest, launcher, version,
  platform). No software is copied into the home.
- The consumer role **fails closed**: if the runtime user can write the store
  root or the layout directories that decide a generation's contents, the install
  is refused with the remediation ("publish from a different account or mount the
  store read-only"), because a writable store cannot prove the bytes are the
  verified ones.
- A home keeps `<home>/configs/agent_references.json` next to the Vault record, so
  backup exclusion, restore and garbage collection can read what the home still
  needs without opening the database.

## Reclaiming per-home copies

`matrix agent prune` converts an existing per-home install into the store-backed
shape without deleting anything by default: it first proves the recorded
generation still verifies, then reports the exact bytes of the superseded copy;
`--apply` removes only that software directory and keeps the Vault record and the
store reference. It refuses an agent without a store reference or whose
generation no longer verifies. Uninstall drops the reference, so garbage
collection can reclaim the generation afterwards.

## Inventory and restore

- `matrix agent inventory` is deterministic and secret-free: agents sorted by id,
  environment reduced to variable names, no install timestamps, no values; each
  agent states whether it is regenerable and which command would restore it. Two
  homes with the same software produce the same document, which is what a
  consumer compares before excluding software from a backup.
- `matrix agent verify` reports `store_tree` (full offline tree verification) for
  store-backed agents and `recorded_evidence` for per-home installs, which proves
  the launcher exists and a verified digest was recorded but does **not** re-prove
  the bytes offline. `--strict` exits non-zero unless every agent is fully
  verified; the two methods never collapse into one claim.
- `matrix agent restore --inventory <file>` reinstalls from a verified store
  generation when the inventory is store-backed, otherwise from the governed
  registry, refuses a registry version different from the inventory unless
  `--allow-version-drift` is explicit, and `--dry-run` reports without downloading
  or writing.

## Measured effect

Measured on the released tree with an isolated two-home smoke (`amp-acp` 0.10.0,
`linux-x86_64`, published generation
`320959bb1de650681413a3fc72febd62fded65c734b9ab3399855e007fcdd1ba`, tree manifest
`17c7d8d2b6adf70357e12dbf6f3ca3467f3734d98597692a32f8db726dcaf2ed`):

- after `prune --apply`, both homes' `agents/` trees measured 0 bytes
  (`du -sb`), while the single store generation measured 81,737,951 bytes;
- the second home was created only by
  `matrix agent restore --inventory inventory-home1.json --store <root>`, without a
  registry download, and `matrix agent verify --strict` reported `store_tree` for
  both homes;
- a store the runtime user could write was refused by the install path
  (measured, not inferred);
- `store gc` dry run with the two homes reported 0 reclaimable bytes, and the
  empty-reference guard refused `--apply` for a wrong `--home` list.

These are measurements of one local smoke, not a promise about a Hub's backup:
the reclaimable size is each deployment's real software directories, and no
savings are declared before that measurement.

## What was deliberately not built

- **No Hub/worker or backup policy change.** Matrix does not edit Hub
  configuration, per-worker inventories, backup schedules or the disk reserve, and
  it does not decide what a consumer backs up. The report's `workers` peak and
  `require_full_backup_capacity` stay the consumer's numbers.
- **No cross-account immutability guarantee.** Matrix validates the permissions it
  can see and refuses a store writable by the runtime user; it cannot enforce that
  a different account or a read-only mount actually exists. On Windows ownership
  cannot be proven, so an owner-writable store counts as writable.
- **No hardlink/symlink conversion and no automatic migration.** The store copies
  verified bytes once at publish time; converting an existing install is the
  explicit sequence publish → install from store → prune. Matrix never rewrites or
  deletes a home's software on its own, and it never deletes consumer data.
- **No per-worker digest audit.** Matrix cannot compare the eight Hub workers'
  trees from this repository; it provides the digest-addressed generation that
  makes such a comparison possible for the deployment.
- **No savings claim.** The release reports the local smoke numbers and the
  commands to measure a deployment; it does not extrapolate a Hub saving.

## Limits

- A store generation is platform-specific (`linux-x86_64`, `darwin-aarch64`, …);
  one store can hold many platforms side by side, but a home only installs the
  generation for its own platform.
- Extraction reuses the existing archive provider, which silently drops unsafe
  archive entries (symlinks, hardlinks, absolute paths). A hostile launcher
  therefore fails closed (missing launcher), while a hostile non-launcher entry is
  dropped and the reduced tree is what the generation publishes and verifies.
- Garbage collection is deployment-coordinated: `gc` trusts the `--home` list it
  is given, refuses `--apply` when that list yields no reference at all, and never
  deletes a referenced generation.
- A store-backed home depends on the store being mounted; if it is not, the agent
  fails to launch visibly instead of falling back to a stale copy. The Vault,
  sessions and agent records are unaffected.
- Matrix verifies declarations and bytes, not agent behaviour: the store
  strengthens the provenance of installed software; it cannot prove what an agent
  does at runtime.
