# Matrix v0.1.62 — measured store footprint and honest verification verdicts

The artifact store released in v0.1.61 could be published, verified and pruned,
but a deployment could not measure it: the consumer was told to run `du -sb` and
to derive the rest. This release adds the measurement Matrix can actually make —
what the store holds, who still references it, and what the next collection would
reclaim — and it stops conflating two different failures on the verification
surface: *the store's role is wrong* and *the bytes are wrong*.

It answers two external reports:

- [Hub adoption of the immutable reuse and the still-unqualified
  benefit](../../../issues/closed/2026-10-26-external-agent-hub-artifact-store-adoption.md)
  — accepted in part: the measurement is built, the adoption and its VPS
  qualification stay with the deployment owner, and the canonical path is
  documented.
- [Knowledge qualification: local OpenCode without an installation
  receipt](../../../issues/closed/2026-10-27-external-knowledge-local-opencode-provenance.md)
  — accepted: the owner path exists and covers it, under a deployment condition
  that this release now states in the verdict instead of leaving as a wall.

## The contract

- `matrix agent store usage --store <root> --home <path>...` measures every
  published generation **from disk** and counts it once, then classifies its bytes
  by how many of the named homes still reference it: **exclusive** (exactly one),
  **shared** (two or more), **reclaimable** (none, so the next `gc` pass would
  delete it). Publish staging is reported apart because it is work in flight, not
  published software. The three buckets add up to the measured total by
  construction. `--home` is required, with `gc`'s discipline: a measurement that
  does not know every home would report live software as reclaimable.
- **Inspecting a store no longer mutates it.** The read-only inspection path used
  to fall back to the publisher role, and opening a publisher rewrites the layout
  permissions — so `store list`, `store verify` and the `gc` dry run could remove
  the seal from a store they were only asked to read. Inspection now opens the
  store without checking or changing a permission.
- **A third verification method, `store_writable`.** A store-backed agent whose
  store the runtime user can write is still measured: the tree must be readable,
  must verify against its published manifest, and that manifest must be the one
  the reference recorded. A match is reported as a point-in-time observation that
  cannot be relied on — those bytes can be swapped after the check — and it never
  verifies. A tampered tree in the same store still reports wrong bytes, because
  that is the fact that matters to the caller.
- **Every verification result carries the remedy it knows.** A per-home binary
  install names the store adoption sequence; an `npx`/`uvx` install declares that
  its package manager leaves no archive for Matrix to publish or re-prove; an
  agent registered by path declares that no registry artifact exists for it; a
  writable store names the deployment fix. The remedy is guidance for the
  operator, never a guarantee Matrix cannot keep.

## Evidence

- A real generation was published from the registry and measured: `opencode`
  2.2.0 `linux-x86_64`, digest
  `6d597970a8cc448f1b9a9f645532584b339dd3ab9583bb5f063f13d83e54768f`,
  **246 831 280 byte**. The same store was measured with one referencing home
  (exclusive), two referencing homes (shared) and none (reclaimable); every
  bucket reported the full measured size, and a run without `--home` was refused
  with exit 1. The measurement store was removed after the observation.
- `matrix agent verify opencode --json` on this host now reports the reported
  case as `recorded_evidence` with the adoption sequence as the remedy, instead
  of failing without saying what would fix it.
- The `store_writable` path is covered by a test that publishes and seals a real
  store, then unseals it: the same bytes must be measured and must not verify,
  and a tampered tree in that store must still be reported as wrong bytes.
- Both governance gates pass with no file, function, parameter or branch budget
  relaxed; the three package ceilings were raised to their measured values with a
  dated justification in `code-governance.toml`.

## What was answered with a limit, not with code

- **The Hub backup peak is not measurable here.** `usage` measures this store and
  the references it is given. Another product's backup peak also depends on its
  compression, its exclude rules and what it does with the store path; Matrix
  does not read or control any of that.
- **No one-time conversion from the existing local bytes.** Publishing from a
  local copy would coin a second identity (a tree digest in place of the archive
  digest) and attest bytes no index verified. The path stays: publish from the
  registry once per platform, install from the store, prune the superseded copy.
- **No receipt for a script-installed per-home binary.** Recording a digest of the
  bytes in place would attest that *those* bytes were there, not that they came
  from the publisher — precisely the false receipt the report forbids. Real
  provenance needs the store.
- **`/_matrix/runtime` still carries no byte-level verdict.** Re-hashing a tree on
  every runtime poll is not a cheap read, and that surface reports install
  evidence rather than a proof. The owner command stays `matrix agent verify`.
- **A single account cannot reach `store_tree`.** The publisher must write the
  store and the runtime user must not; where one account does both, the verdict
  is `store_writable` with the deployment fix as its remedy. That is a property of
  the deployment, not a defect this release hides.
