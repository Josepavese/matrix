# Matrix v0.1.64 — a stale launch declaration cannot outlive a configuration change

An existing ACP client could survive a changed launch environment. The cache
comparison returned a match immediately when neither the cached nor the resolved
endpoint declared a sandbox, before comparing the declarations at all. The cache
key covers agent, workspace and launch arguments, not the resolved environment:
change `OPENCODE_ENABLE_EXA` from `0` to `1` without touching agent, workspace or
arguments and Matrix kept reusing a child that had been started with `0`, while
the updated endpoint configuration was silently presented as the running child's
configuration.

This release answers two reports:

- [ACP client cache ignores changed launch environment without a sandbox](https://github.com/Josepavese/matrix/issues/19)
  — accepted: the comparison gap is real and fixed here. A changed resolved
  declaration is detected for nonsandboxed clients too, the new dispatch fails
  closed through the existing explicit reap/relaunch workflow, and active leases
  and unrelated sessions are left untouched. An unchanged declaration replays the
  cached client.
- [Expose privacy-safe offered tool catalog evidence per ACP model request](https://github.com/Josepavese/matrix/issues/20)
  — accepted, answered with a limit: the tool catalog a provider offers to a
  model is provider-owned and is not carried by ACP v1, so Matrix does not
  publish an attestation it cannot observe. The trace contract now states that
  boundary explicitly — absence is `not_observed`, never an empty catalog — and
  points to the provider-side instrumentation a consumer needs.

## The contract

- **The launch declaration is compared as a whole, for every ACP client.** The
  early return for endpoints without a sandbox is gone: `cachedLaunchMatches`
  serializes the cached resolved endpoint and the currently resolved one and
  compares them, so a changed environment, argument, command, address or other
  launch field invalidates the cached child. The sandbox case keeps its existing
  behavior and test.
- **A mismatch fails closed, preserving what is in flight.** The dispatch is
  refused with `launch declaration changed: reap the previous workspace client
  before dispatch`; the cached client is not evicted from the cache, not closed,
  and its active lease is not touched. Other workspaces and their sessions are
  unaffected. The operator completes the existing explicit reap/relaunch
  workflow; Matrix never presents the updated configuration as the stale child's.
- **An unchanged declaration replays.** With the same resolved declaration, the
  cached client is reused rather than reaped and relaunched, so the fix adds
  detection without turning normal dispatch into a restart loop.
- **What the trace cannot observe is now documented.** The offered-tool catalog
  is provider-owned; configured capability, executed calls and a model's
  statement are different observations and none is the model's request catalog.

## Evidence

- Three new regressions: a nonsandboxed cache entry stops matching when the
  resolved environment changes; a changed declaration fails closed in
  `getOrCreateClientLocked` without evicting or closing a client that holds an
  active lease; an unchanged declaration replays the same cached client. The
  existing sandbox-policy comparison test still passes.
- Two test scaffolds were corrected to model real clients rather than the old
  bypass: the concurrent-cancel fake now carries the resolved endpoint it was
  created with, and the child-working-directory probe restores the first
  workspace's declaration before replaying it (its resolver switch is test
  scaffolding, not a live endpoint change).
- Full suite green, including `go test ./internal/providers/agents`; both
  governance gates pass with no package, file, function, parameter or branch
  budget raised.

## What was answered with a limit, not with code

- **No offered-tool attestation.** The requested evidence is the tool catalog a
  provider placed in a model request. ACP v1 does not transmit it: `initialize`
  and `session/new` carry capabilities and session facts, not tool names. An
  attestation with names and a digest would be narration, not observation, and
  the absence would be misread as an empty catalog. The boundary and the
  provider-side mechanism are documented in the trace contract instead.
- **No new CLI/API/trace read path for that evidence.** There is no owner data to
  read. A field that always says `not_observed` adds no observation; the contract
  already forbids presenting configured capability or executed calls as the
  model's request catalog.
- **No automatic reap of the in-flight child.** The report asks to preserve active
  leases and fail closed through the existing explicit workflow; killing a child
  under a live lease would be the opposite. The mismatch is reported, the client
  stays, the operator reaps when its leases allow.
- **Partial or lost prompt acknowledgements stay turn-lifecycle evidence.** The
  cache decision happens before dispatch, so no result from the stale child can
  be presented as the updated configuration's; the new tests qualify that ordering
  rather than changing the acknowledgement protocol.
- **A resolver that cannot answer now fails the reuse instead of silently reusing
  a client without checking.** That is the fail-closed price of the guarantee and
  matches the existing sandbox path.
