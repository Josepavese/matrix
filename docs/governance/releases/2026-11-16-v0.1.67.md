# Matrix v0.1.67 — interleaved tool calls keep their own trace identity

Matrix v0.1.66 qualified ACP version 2 as a preview and left version 1 as the
stable path. This patch fixes a trace-correlation defect found after that
release: when a turn had more than one tool call in flight, a completion could
be written under the identity of the most recent request instead of the call it
actually belonged to.

The defect was provider-neutral. It affected the persisted run trace, so an
audit or replay could mis-attribute a result even though the turn itself had
completed correctly. It is not an ACP v2 negotiation change and does not promote
the draft protocol to stable.

## The defect

Reported as [issue #21](https://github.com/Josepavese/matrix/issues/21) and
reproduced on `0dbf06d` with this sequence:

```text
request A -> request B -> completion A -> completion B
```

The notifier kept only the last requested call (`activeToolCallID`) and preferred
that slot over the peer-assigned identity carried by the completion metadata.
Completion A was therefore persisted as completion B, and request A was left
without a completion carrying its own ID. Classification and path/operation
context inherited from the last request could be wrong for the same reason.

## The fix

- The call identity extraction is now one shared helper,
  `frontendevents.ToolCallID`; `StableToolCallID` uses it instead of carrying a
  second copy of the metadata precedence.
- The notifier tracks every open call in a map keyed by its trace identity, with
  the last-request slot retained only as the fallback for a peer update that
  carries no identity of its own.
- A completion that arrives with an explicit `tool_call_id` is correlated by that
  ID first. Its inherited name, kind, classification, path and operation come from
  the matching open call, not from whichever request happened to be newest.
- A terminal completion removes only its own call from the open set. Other calls
  remain correlated for their later updates.
- Permission enrichment updates the open call it belongs to, preserving the
  existing behavior where a permission path completes the requested tool
  context.

No provider name, protocol-version branch or channel-specific path was added.
Version 1 remains the stable served path.

## Evidence

- `TestNotifierCorrelatesInterleavedToolCalls` reproduces request A, request B,
  completion A, completion B and asserts each completion keeps its request ID
  and its own path context.
- The existing permission-context correlation test also passes, covering the
  shared enrichment path this change touches.
- `go test -race ./internal/logic/runnotifier ./internal/logic/frontendevents`
  is green.
- `scripts/release_gate.sh` on `e7a95da` reported `RELEASE_GATE_OK`: archived
  commit, Linux/Windows/macOS builds, vet, nine race packages, governance,
  code budgets and every coverage floor passed.

  Release run `43883293771` published the tag.
- `scripts/verify_release.sh v0.1.67` reported 88 checks ok, 0 failed,
  `RELEASE_VERIFY_OK`: six archives, six SPDX SBOMs, checksums, installer
  assets and a provenance attestation for every archive digest.
- An isolated PAL home installed from the published `install/install.sh`
  reported `matrix 0.1.67`, commit `e7a95dacc1737634c255313a296123dca4b278ab`.
- Issue #21 is closed by the fix commit.

The live PAL home is a deployment boundary, not part of publishing: it still
runs `0.1.66` until an operator performs the backup-protected replacement and
restarts the runtime. The published artifact and its installer were verified
independently of that running process.

The fix applies to newly written traces. Historical run events are not rewritten:
they remain the record of what the old build observed, and a backfill would
invent observations that were never made.
